# Poa for open-source collectives

A useful library soon needs more than code. People need examples, reliable installation instructions, maintenance, and a way to influence what gets attention. Much of that work happens around the repository.

Keep your repository and development tools. Poa lets the people doing that work earn a stake in the organization behind the project, influence its funded roadmap, and check how shared resources are used.

## Get to the next release

Imagine an accessibility library preparing a stable release. It has funds available for maintenance and two competing priorities: improve keyboard navigation or add a component users have requested. The people reviewing issues and supporting users have experience that should inform that investment.

The collective could use contribution-weighted binding votes among eligible members to allocate work funding, with rewards recognizing documentation and review as well as code. That arrangement gives sustained maintenance a role in directing the budget. It could add an equal-member class if it wants members with small balances to carry more weight.

For the chosen release work, create [tasks](/docs/task-manager) linked to the relevant issues or pull requests. Set participation rewards, any funded bounties, and reviewers. Contributors can inspect that agreement before taking a task.

Review the result in your existing development tools, then approve completion of the corresponding task in Poa. That awards the configured reward; merging a pull request alone does not trigger it.

## Give contributors a path to responsibility

A useful contribution can earn more than a thank-you. Participation rewards can give someone weight in the project's decisions under its configured rules. The group can also approve revenue distributions when it has funds to share.

A contributor who starts with a translation might later maintain the language pack or propose a new direction for the interface. Include documentation, reviews, support, and maintenance in the reward system so that this path is open to more than the people writing code.

Make [joining](/docs/join) and review straightforward: name a reviewer, explain what they will check, and show what the task earns. Describe how a contributor can take on maintenance or review responsibilities as they gain experience.

## Fund and govern the project

A contributor who has spent months improving documentation can use their eligible voting weight when the collective considers another release budget. A [binding proposal](/docs/hybridVoting) can authorize the supported payment or permission change, and members can check its execution.

If the library later earns revenue, the group can decide what to retain for maintenance and what to distribute. [Treasury tools](/docs/treasury-management) create deliberate, funded allocations based on a recorded snapshot; eligible recipients claim their share. Neither a task reward nor a successful release creates an automatic payout.

Keep copyright, licensing, and repository ownership explicit alongside [participation rights](/docs/contribution-and-ownership). Poa's contribution records do not change those arrangements.

## Connect the tools you already use

[Create an organization](/docs/create) and link its tasks to the issues you want help with. Put the organization link in your contributing guide so someone arriving at the repository can find the work, rewards, and membership rules.

Later, you can give the organization an entry point on [your own domain](/docs/white-label-hosting), or build a release dashboard from its [public records](/docs/TheGraph). Those tools need their own setup and maintenance, but they can work with the organization you already have.
